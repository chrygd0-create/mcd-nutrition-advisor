## 这是什么问题

每个人都知道巨无霸是 500 多大卡。但没人能在点餐的三秒钟里回答真正的问题：

> **「我今天还剩 500 大卡预算，麦当劳里到底能吃什么？」**

于是人们只有两个选择：要么瞎点然后后悔，要么干脆不吃。

现有的「麦当劳热量表」基本都是第三方爬取的静态数据，过期、且不含钠。而麦当劳 MCP 官方提供了 `list-nutrition-foods`
工具，包含能量、蛋白质、脂肪、碳水、钠、钙的实时数据 —— **官方数据接口一直都在，只是没有人把它和「用户的热量预算」这道算术题连起来。**

本Skill 就是做这一件事。

## 它做了什么

```
用户："我在减脂期，今晚只能吃 500 大卡，麦当劳能点什么？"
                            ↓
Skill  ── list-nutrition-foods  → 官方营养成分（含钠）
       ── query-meals→ 当前门店真实在售
       ── available-coupons     → 你手上能用的券
       ── campaign-calendar     → 正在进行中的活动
       ── calculate-price       → 真实应付价
                            ↓
输出："板烧鸡腿堡 + 鲜煮咖啡（中）
       485 kcal｜蛋白 28.3g｜钠 1032mg｜¥31
       预算利用率 97%，无糖饮品不占热量配额。"

  # 三个要点：热量是官方的、菜单是当下在售的、价格是真算出来的。
```

### 核心能力

| 能力 | 说明 |
|------|------|
| **目标感知配餐** | 减脂 / 维持 / 增肌三套模型，热量系数与蛋白目标自动切换 |
| **预算硬约束** | 本餐热量上限是硬门槛，绝不返回超预算组合 |
| **热量 × 优惠券联合优化** | `value` 模式把实付价放进目标函数：同样的热量预算，券后最便宜 / 性价比最高的组合直接给答案 |
| **团购跨渠道比价** | 抖音/美团团购作为独立支付路径与官方券同台比价；整套未凑齐不出路径，第三方渠道强制用户确认后才能买 |
| **外送全链路** | 选地址 → 查可配送门店 → 外送菜单配餐（orderType=2）→ 含配送费算价 → 确认下单；地址电话不落任何文件 |
| **凑单反赚提示** | 检测「差 2 元到满减门槛 → 加份小食用券 → 实付反而更低」的场景，主动提示 |
| **钠维度告警** | 减脂期钠超标（>800mg）会显式扣分并提示，主流热量表忽略这一点 |
| **真实省钱计算** | 叠加 `calculate-price`，输出「同样营养目标下省了¥X」 |
| **活动感知** | 引导查询活动日历与积分抽奖，把「今天有什么活动」一起答了 |
| **全链路闭环** | 配餐 → 算价 → 用户确认 → `create-order` |

### 为什么和别的不一样

| 对比项 | 静态热量表 | 本 Skill |
|--------|-----------|---------|
| 数据来源 | 第三方爬取、经常过期 | 麦当劳 MCP 官方接口 |
| 菜单时效 | 全量菜单，可能已下架 | `query-meals` 过滤当前门店在售 |
| 价格 | 常缺失或为估算 | `calculate-price` 真实计算 |
| 输出 | 让你自己判断 | 直接给可下单的组合 |
| 钠 | 通常不提供 | 官方数据，含阈值告警 |

## 快速开始

### 方式一：在 WorkBuddy 中使用（推荐）

**第 1 步· 申请 MCP Token**

打开 https://open.mcd.cn/mcp → 右上角【登录】→ 手机号验证 → 右上角变【控制台】→ 点【激活】→ 同意服务协议 → 复制 Token。

**第 2 步 · 配置连接器**

WorkBuddy 左侧边栏【连接器】→ 右上角【自定义连接器】→【配置MCP】，填入：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer YOUR_MCP_TOKEN"
      }
    }
  }
}
```

把 `YOUR_MCP_TOKEN` 换成你的 Token →【保存】→ 回到连接器列表启用 `mcd-mcp`。

**第 3 步 · 安装 Skill**

把 `skill/` 目录放到 `~/.workbuddy/skills/mcd-nutrition-advisor/`（或项目内 `.workbuddy/skills/`）。

**第 4 步 · 开始提问**

```
我在减脂期，今晚只能吃 500 大卡，麦当劳能点什么？
增肌日 900 大卡预算，给我配一份麦当劳
我手上有几张券，帮我算算怎么点最划算
500 大卡预算，用我的券，怎么点最便宜？
送我家里来 —— 我减脂期，500 大卡，直接帮我点外送
```

### 热量 × 券联合优化的实际效果

以「维持目标 / 700 大卡预算 / 手持满30减8 + 满45减15 + 麦乐鸡5元券」为例（自测数据）：

| 优先级 | 推荐组合 | 热量/蛋白 | 价格 |
|--------|---------|----------|------|
| economy（最便宜） | 板烧鸡腿堡 | 480kcal / 28g | ~~¥21~~ → **¥16**（麦乐鸡5元券） |
| balanced（性价比） | 板烧鸡腿堡 | 480kcal / 28g | ~~¥21~~ → **¥16**，每10元换17.5g蛋白 |
| protein（蛋白最高） | 吉士汉堡 + 麦乐鸡(5块) | 690kcal / 39g | ~~¥33~~ → **¥25**（满30减8券） |

同样的热量预算，三种问法三个答案，每个都是算过券的真实价格。

## 计算引擎的设计取舍

引擎（`nutrition_calculator.py`）里有几个不那么显然但很关键的决策：

**1. 小食与饮品是可选槽位，不是必选。**
最初实现强制每餐「主食 + 小食 + 饮品」，结果在 500 大卡预算下只可能返回「咖啡 + 无糖可乐」这种无意义组合。
正确做法是枚举槽位的所有取舍：`主食` / `主食+小食` / `主食+饮品` / `主食+小食+饮品`，让「汉堡 + 零卡饮」成为合法解。

**2. 排序目标是「蛋白收益 − 闲置预算惩罚」，不是纯蛋白密度。**

```python
unused = max(0.0, budget_kcal - t["kcal"])
value  = t["protein"] - unused * 0.05
```

纯按蛋白密度排会让维持热量预算大量闲置（实测485/800，白扔 315 大卡）；纯按蛋白总量排又会让减脂期塞进过多小食。0.05 这个系数是让预算利用率稳定落在 93%–99%。

**3. 零卡饮品不能霸榜单品推荐。**
无糖可乐在评分上天然碾压一切（热量几乎为0），但「推荐你喝一杯无糖可乐」对用户没有决策价值。
因此单品榜在正餐候选充足时（≥2 个）只保留一杯饮料且排在正餐之后。

**4. 增肌目标优先选含糖饮品。**
训练后补碳水有实际意义，所以 `gain` 模式下含糖饮品的优先级被提到咖啡和零卡之上。

**5. 分类缺失时绝不用饮品兜底当主食。**
真实菜单可能不返回标准分类。降级策略严格限制为「非饮品类最高分」，
宁可少配一档，也不输出「麦乐鸡 + 咖啡」这种不像套餐的组合。

**6. 蛋白优先级要按克取整分桶，再比价。**
`value --priority protein` 最初直接按蛋白排序，结果「39.3g/¥35（加咖啡）」排在「39.0g/¥25」前面
—— 为 0.3g 蛋白多花 10 元，用户不会买账。取整分桶后同档内只比价格。

**7. 优惠券在枚举阶段就进目标函数，而不是算完再叠。**
如果先选营养组合再查券，会错过「换个组合刚好过满减门槛」的解。
`value` 模式对每个候选组合直接计算券后实付价参与排序，
并额外扫描「加一件小商品过门槛后实付反而更低」的凑单机会。

**8. 团购券整套出售，未凑齐就不出路径。**
第一版允许部分覆盖（组合只含团购套餐的一半），结果输出了「¥24.9 覆盖 1 件」的怪路径。
现实中团购券不可拆用、不可与官方券叠加，所以规则收紧为：组合完整包含团购套餐才生成路径，
路径上必须带整套热量与确认提示（第三方渠道，购买前用户确认）。

以上每一条都来自实测发现的错误输出，`skill/selftest.py` 固化了回归验证。

## 安全与合规

- **Token 仅通过环境变量 `MCD_MCP_TOKEN` 读取**，代码、日志、输出中均不含真实凭证。
- **下单类工具（`create-order` / `mall-create-order` / `draw-lottery`）必须二次确认**，调用前完整复述餐品与金额。
- **不提供医疗或营养治疗建议**，输出附免责说明。
- 本项目为参赛作品，非麦当劳官方产品；餐品信息与价格以官方渠道实时结果为准。

## 目标用户

- 减脂 / 增肌期但不想彻底放弃快餐的人
- 健身教练与营养师（做快速配餐估算）
- 关心钠摄入但无处查询的消费者
